# FitFam User Management System (UMS)

The **internal admin website** for the FitFam team. It is not for customers.

> **Status: fresh scaffold only.** This is an unmodified `create-next-app` project. There are no pages beyond the
> default starter, no authentication, no database and no integration with the FitFam API yet. This README describes what
> exists now and, clearly marked, what is planned.

**Audience:** the FitFam team only.

## Quick start

```bash
git clone https://github.com/yotamblu/fitfam-ums.git
cd fitfam-ums
npm install
npm run dev
```

The dev server starts on http://localhost:3000 by default. **The customer app (`fitfam-web`) also uses port 3000**, so if
you run both at once, start this one on another port:

```bash
npm run dev -- -p 3001
```

## Available scripts

| Command | What it does |
|---------|--------------|
| `npm run dev` | Development server |
| `npm run build` | Production build |
| `npm run start` | Serve the production build |
| `npm run lint` | Run ESLint |

No test command exists yet.

> Do not run `npm run build` while `npm run dev` is running in the same folder: both use `.next`, and the dev server will
> break. Stop dev first, or delete `.next` and restart dev.

## Configuration and secrets

There are no environment variables yet. When they are introduced:

- Keep them in a local `.env.local` (already gitignored by the `.env*` rule), never in committed files.
- Production secrets live only in the hosting provider's environment variables.
- Variables prefixed `NEXT_PUBLIC_` are shipped to the browser. Never put a secret in one.
- Never commit secrets.

## Access control (planned)

This site manages real customer data, so it must be locked down before it holds any:

- Only authorised team members may access it (an explicit allowlist of admin accounts).
- Sign-in should follow the FitFam rule of Google Sign-In only, verified server-side.
- It should live on its own subdomain and must not be linked from the customer app.
- No customer data should be present in this repo.

How exactly the admin allowlist is stored and enforced is not decided yet.

## Open decisions

Not decided; do not assume:

- **Data access:** the rest of FitFam keeps the database behind the Spring Boot API. Whether the UMS goes through new
  admin endpoints on the API (consistent with the architecture) or has its own data access is undecided.
- Which database and schema (not designed yet).
- Hosting for the admin site.
- Whether to keep an audit log of manual changes.
